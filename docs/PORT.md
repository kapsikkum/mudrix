# Porting Mudrix onto this base

Inventory of everything Mudrix (`E:\code\web\mudrix-web`, branch `port/last-upstream`, plus the `mudrix-desktop` and
`mudrix-mobile` shells) adds beyond upstream WizardChat web, and what this repo (the Rust-core rewrite) already has.
Read-only research; nothing was built or run. Where a claim was inferred rather than read, it says "unverified".

## How to read this

- **Source** paths are relative to `mudrix-web/` unless they start with `desktop:` (`mudrix-desktop/src-tauri/src/`) or
  `mobile:` (`mudrix-mobile/src-tauri/`).
- **Class**
  - `UI-only`: can be built in `apps/web` on the existing generated API (`setAccountData`, `setStateEvent`,
    `sendEvent`, `setProfileField`, `uploadMedia`, `media`, `searchMessages`, ... see `crates/core/src/rpc/`). Because
    `docs/CONTRIBUTING.md` makes `apps/web` the reference that `apps/ios` and `apps/android` must mirror, every UI-only
    row is web first and then 2 more native ports (not counted in size).
  - `needs-core-RPC`: needs a new method in `crates/core` (and `npm run core:types`). The capability is named.
  - `platform-shell`: Tauri Rust or native iOS/Android code (`apps/desktop/src-tauri`, `apps/ios`, `apps/android`).
  - `infra`: CI, docs, tooling, repo files.
- **Base?** is what this repo has today: `yes` (path), `partial` (what is missing), `no`, or `parity gap` (an upstream
  WizardChat feature the base lacks; Mudrix inherited it from upstream, so the port must still bring it).
- **Size** S (under a day), M (1-3 days), L (a week or more), for the web UI only.
- **Batch** is the suggested order, 1 first. Phase 2 = UI-only batches P2-x; phase 3 = core batches P3-x; shells are P4-x.
  See the batch plan at the end.

Shorthand: `base/web` = `E:\code\web\mudrix\apps\web\src\app`. `core` = `E:\code\web\mudrix\crates\core\src`.

## Scale of the divergence

527 non-merge commits since `6ed2b0af`, 1021 files, +116k/-11k lines. Mudrix web is a matrix-js-sdk app; this base moves
all Matrix logic into `crates/core` (matrix-rust-sdk), so nothing Mudrix does with `MatrixClient` ports as is. Anything
that talks to the homeserver from app code (CONTRIBUTING: "never raw HTTP to the homeserver") must go through a new RPC.

## (a) Top-10 risks

1. **Three UIs.** `docs/CONTRIBUTING.md` says apps/ios and apps/android are "the same app twice" and mirror every web
   change. Each UI-only row (themes, soundboard, cosmetics, integrations, spaces) is therefore roughly 3x the stated
   size, or a deliberate decision to ship web/desktop only first. Decide before phase 2 starts.
2. **Namespace and data compatibility.** Mudrix writes `io.github.kapsikkum.mudrix.*` (reading `chat.mudrix.*`, and a few
   `io.mudrix.*`/`org.mudrix.*`) in account data, room state and profile fields (`src/util/namespace.ts`); this base and
   upstream use `org.wizardchat.*`. Settings sync, cosmetics, roles, categories, saved messages, voice-move, watch topic
   and soundboard data all hinge on it. Pick one prefix, keep reading the old ones, and test with a real Mudrix account.
3. **i18n debt.** The base requires identical keys in every language and `npm run check` enforces it. Mudrix has 11
   languages with inline `defaultValue`s and a different key tree; only `en` and `de` exist here. Each batch adds keys
   that need real translations.
4. **Design-token model.** Themes are build-time JSON in `packages/design-tokens` that iOS/Android consume. Custom
   themes (A2), 29 built-ins and "a new colour must go into every theme" need a generator/derive step in three
   languages. Mudrix' `onAccent`, scrim, elevation tokens will collide with base tokens.
5. **js-sdk escape hatches.** Many Mudrix features call `client.http.authedRequest` or `_unstable_*` (delayed events,
   timestamp-to-event, shared rooms, federation version, relations). All need new core RPCs and `npm run core:types`;
   they cannot ship in the web UI without breaking the "no raw HTTP" rule. See (c).
6. **Third-party network access from UI.** Integrations (I3/I4) and link details fetch external hosts; the YouTube
   embed, GIF providers and homeserver-software probe do too. The base has no generic outbound-fetch surface except
   `urlPreview`. A policy (CSP allow-list per integration vs core RPC proxy) is needed before I1-I4.
7. **Code-running widgets.** I5 runs third-party code in a sandboxed iframe with a matrix-widget-api driver on
   js-sdk. Needs a real core-side driver and a security review; Mudrix had several hardening commits here ("fixes
   from the security review").
8. **Desktop shell surface.** Tray, badge, toasts, popout, permissions and download sanitising are ~1800 Rust lines in
   Mudrix' shell. The base desktop shell is far smaller and on GitLab updater feeds; wholesale copying risks conflicts
   with `apps/desktop` (`lib.rs`, `rpc.rs`, `update.rs`). Port module by module with the base's `cfg`s.
9. **Unread/receipt/room-list behaviour changes.** Mudrix has ~15 fixes that work around js-sdk counting (receipt scan,
   thread unread, DM heuristic, "ignore join/leave"). The Rust SDK computes these differently; blind porting reintroduces
   bugs, skipping them loses parity. Needs scenario tests on the local test server (E1).
10. **Platform-specific media and background work.** Video compression, EXIF stripping, spellcheck and activity
    detection have no shared implementation: WebCodecs/canvas/hunspell-wasm on web+desktop, separate encoders and
    system spellcheck on iOS/Android, Windows-only detection. Also UnifiedPush/keep-alive have no equivalent in the
    native apps yet.
